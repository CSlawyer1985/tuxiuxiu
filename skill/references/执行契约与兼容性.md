# 执行契约与兼容性

分享版可分发已明确许可的Google官方皮肤模型及平台运行库；来源、摘要、实际推理自检和安装边界见 [分享安装与皮肤模型](分享安装与皮肤模型.md)。这项特定资源分发不扩展到专有厂商素材或活动照片，模型候选不自动获得质量批准。

版本 2.0，2026-11-05。与《修图业务规则》共同适用。本文件解决人工审计记录、资源与状态之间的联系；可执行网页管线另见 [自动批量管线与网页选样](自动批量管线与网页选样.md)。两种记录结构分别核验，不把运行数据库冒充完整审计模板。照片质量仍由每批真实样片验收。

## 1．三个根与运行依赖

- **Skill 根**：只存本包说明、模板与脚本。包内链接从本包读取，不写入活动材料。
- **活动根**：一次活动的 `input/`、`scratch/`、`output/` 与活动记录。批次 JSON 内路径为活动根下规范相对路径，不含上跳、绝对路径或软链。
- **外部源**：用户指定的照片或素材来源。只读盘点，复制到活动后核对摘要；不覆盖、移动或清理外部原件。

业务核心不读取本机共享目录、其他软件缓存或另一 Skill。宿主自身的指令仍适用，但由宿主适配。包内检查脚本需要 Python 3.10 及以上；图像检查需要 Pillow。实际调色可使用当前可调用的 NumPy、OpenCV、专用传统工具或原生软件；按需核对 ICC、浮点、滤波与导出能力，不以库名推定人像检测可用，不自动安装依赖。

“自包含”指业务规则、记录语义、检查逻辑及当前传统像素管线源代码在包内齐备，不表示捆绑 Python、完整商用修图引擎、所有模型或厂商素材。缺少可选 LUT、检测器或滤波器时，继续可完成的部分，明确停用项与替代方式。

## 2．格式与颜色边界

只读盘点用实际文件头解码，不按后缀认定格式；逐项报告不可读、非图像与软链。可打开不等于所选处理器保留了原始位深、透明通道或颜色语义。

| 输入 | 执行前必须核对 |
|---|---|
| JPEG／普通 RGB PNG | 原始方向、ICC／Exif 声明、编码位深、色度抽样及已有压缩；不冒称 RAW |
| TIFF／16 位／浮点／灰度 | 实际解码位深和通道映射、处理与保存链是否保真；不支持时单列，不静默降为 8 位 |
| CMYK／广色域 | 使用有效配置完成颜色转换，声明意图与输出配置；不简单贴 sRGB 标签 |
| RGBA／透明素材 | 保留透明度，明确预乘／非预乘及混合域；未经允许不铺底或丢 alpha |
| RAW／HDR／HEIF 等 | 仅在当前已验证的解码器和色彩流程可用时处理，另记解码参数与高动态范围解释 |

解码后的工作图先按 Exif 整理逻辑方向；蒙版全部使用该方向。导出像素与方向标签必须一致，不把原方向标签复制到已经转正的像素上再次旋转。保留原件元数据；导出只保留工具实际支持的拍摄信息。不要向日志或通用包输出 GPS、账号或与任务无关的元数据。

## 3．配方、资源与未知字段

自有配方使用独立 schema、执行器版本与允许模块。每个模块记录 `applied`、`not_needed` 或 `unavailable`，都有理由；执行时还要写实际算子、颜色域、参数值和单位、区域与资源引用。字段未评估时不能填已完成。外部字段只作为研究数据，审核后手动映射到已验证模块；不执行任意命令、插件或隐藏步骤。

可选的机器校验配方形式为 `retouch-recipe-1`，字段说明见下表；详细人工记录继续使用《基础调色与肤色精修》模板，不能用简化校验记录替代它。

| 字段 | 内容 |
|---|---|
| `executor` | `name` 与 `version`，对应实际工具及执行脚本版本 |
| `color` | `input`、`working`、`output`、`domain`、`channels`、`range` 均为明确说明 |
| `modules` | 过程模板中的 11 个模块各一条：`name`、`decision`、`reason`；执行项另有 `operator`、`parameters`、`mask_ids`、`resource_ids` |
| `parameters` | 列表项含 `name`、`value`、`unit`；仅允许有限 JSON 数值，不接受重复键、NaN 或溢出 |
| LUT 执行项 | `calibration_evidence_id` 指向本图绑定的资源型校准报告，另有实际 LUT 与采样记录；只有字段存在不能证明校准成功 |

运行时仍由助手审核模块语义与数值范围。检查器不解释任意工具的配方、不会执行它，也不能证明声明的参数确实用于渲染。

曲线要明确工作域、x／y 成对表示、端点和插值；拒绝重复 x、非有限数、缺点和越界，检查灰阶单调与色带。HSL、阴影／中间调／高光分级和相机校准是不同职责，不能静默互换。厂商开关、系数、负数和多个 alpha 分别登记，未解语义不取绝对值、不裁成零、不当百分比。

LUT 按真实文件头、摘要、尺寸、位深、通道／alpha、布局、颜色解释、采样与混合语义建立兼容记录。当前已验证的 512×512、64 阶格式不自动覆盖 JPEG LUT、尺寸例外或其他图集。资源有颜色元数据不代表应按普通照片转换其数值表；依具体校准决定。不能缩放异常资源使其“兼容”。

多步骤预设要分别登记处理资源、展示资源、运行蒙版与可选分支，检查缓冲和蒙版引用。不能按 UI Path、文件名或第一张 LUT 认定执行链；未知步骤或依赖使该模块停用，其他已验证模块仍可执行。外观配方与活动水印、输出尺寸、画质分别管理。

## 4．蒙版必须绑定到原图

每张蒙版记录：唯一 ID、原图 ID 与 SHA-256、自身路径与摘要、逻辑方向尺寸、坐标域、用途、原始像素羽化半径、权重解释、覆盖／低置信部分及核对证据。保护区、皮肤作用区与五官排除区分别保存。颜色阈值和人物矩形只是候选，不能直接标成精确皮肤选区。

机器校验路径使用与工作图同尺寸、方向已整理的 8 位灰度 PNG，0 表示不作用、255 表示全作用。浮点或低分辨率蒙版先按已验证映射生成该审计副本，保留原始蒙版及映射记录；这不授权用审计副本覆盖原件。`source_id`、`source_sha256`、`coordinates=oriented_pixels`、`size`、`feather_px`、`purpose` 与 `review` 必须齐备。肤色执行项必须引用 `purpose=skin` 的核对后蒙版。

像素锁定核心的 255 区域在无损基准与无水印工作母版之间核对；羽化过渡另作视觉检查。锁定区不得遗漏已确认的事实内容，颜色和文字保护仍需目视。JPEG 重新编码和独立水印合成不适用逐像素相同保证。

## 5．样片、确认与状态

`批次绑定模板.json` 是空白草稿。其状态为：

| 状态 | 含义与允许动作 |
|---|---|
| `draft` | 盘点、归档或记录准备；检查通过只代表已有文件摘要正确 |
| `sample_ready` | 已有原图、无 LUT 基础候选、完整候选、必要细节、核对后蒙版、配方、运行能力与逐项 QA；可以展示选样 |
| `approved` | 除上述条件外，还有对应样片摘要绑定、范围和用户原话快照；助手须确认原话真实表达批准 |
| `delivery_ready` | 已按批准范围处理，输入输出对应齐全，导出复核已记录；可提交本次交付 |
| `delivered` | 实际向用户给出链接或文件后另记交付事件；工具不会自动产生这个事实 |

样片绑定摘要由选中的原图、配方、蒙版、资源、无损基准／母版、预览、QA、蒙版核对材料，以及颜色、工具、交付与覆盖条件共同计算。用户确认应注明这一批及覆盖条件、所选方案和版本。改了样片配方、选区、资源或确认范围，原确认不能自动批准新样片；同一批新增已覆盖条件的照片不因此重新确认原样片。改变蒙版坐标只针对该图，不能复制到新图。

脚本不会把“更喜欢通透”等自然语言自动转换为批准。`approval` 是助手根据真实对话填写的记录，检查器只能验证它绑定了哪一版，不认证用户身份或批准语义。水印确认仍需涵盖内容、资产、位置、比例和视觉版本；仅指定右下角并不自动批准一个新资产。

批次记录结构：`batch_id`、`state`、`scope`、`artifacts`、`source_ids`、`photos`、`pending_input_ids`、`excluded_inputs`、`sample_set`、`approval`、`deliveries`。每个 artifact 有 `id`、`role`、规范相对 `path` 与 `sha256`，不可一条路径冒充两个角色。每张照片按模板绑定原件、配方、选区、资源、基准、母版、基础预览、完整预览、细节与 QA。`scope.shared_asset_ids` 包括能力检查记录和必要公共资源／水印；不把本机账户或原始研究缓存当共享依赖。

`source_ids` 列明本批全部目标原件，与 `role=input` 的登记项一致；每项必须且只能属于已处理 `photos`、待处理 `pending_input_ids` 或排除 `excluded_inputs` 之一。排除项记录 `input_id`、`reason`、`evidence_id`（复核记录或用户原话），不得静默漏图。样片阶段可有待处理项，交付阶段不得有待处理项。登记清单还需与只读盘点对账；脚本不自动证明未登记的外部目录已经全部遍历。

QA JSON 的 `binding` 要含本图 `input`、`recipe`、`baseline`、`master` 摘要，以及 `masks`、`resources` 的 ID→摘要映射。`checks` 包含 `source_integrity`、`geometry`、`color_units`、`clipping`、`protected_content`、`skin`、`texture`、`watermark`；每项为 `pass` 或有实际理由的 `not_applicable`，通过项附 `evidence_ids`。缺失、失败或未测不得填通过。语义错误、虚构检查仍需助手复核，不能由结构校验洗成真实结果。

`delivery_ready` 还需完整 `deliveries`：每条对应 `input_id`、唯一 `output_id`、`variant`、`expected_oriented_size`、`export_review_id`。同一原件可有已授权的有／无水印等多个版本；同一原件与 `variant` 组合不重复，不以多个版本冒充多张已处理原片。

导出复核为 `role=review` 的 JSON：`schema_version=retouch-export-review-1`；`binding` 含具体 `input`、`master`、`output` 的 SHA-256，不能引用另一版母版或旧成品的复核。`checks` 包含 `format`、`profile`、`bit_depth`、`quality`、`subsampling`、`orientation`、`openability`、`watermark`、`visual`，逐项记录实际检查结果 `pass` 或有依据的 `not_applicable` 及 `reason`。复核材料保存实际编码、ICC、位深、质量与抽样等测量。机器检查核对结构、摘要绑定、对应、尺寸与方向，不替代目视或认证人工声明。

## 6．中断与续跑

每次运行分配唯一 run ID，把输入摘要、配方／选区／资源摘要、逐图状态和已生成路径记在活动 `scratch/`。先在新的过程版本产出，完成核验才列入交付清单；最终路径已存在时不覆盖，产生新版本。

中断后先核对现有文件。只有输入、配方、蒙版、资源与输出摘要都匹配，且对应检查已完成时才可复用该图；部分文件存在不代表成功。摘要不符、失败或未测的条目重新生成到新版本，保留问题版本与原因，不把损坏输出当缓存命中。`batch_contract.py` 只审计；`retouch_pipeline.py` 按独立工作流记录续跑，不移动或删除原件。

重复输入按摘要去重登记；同名不同摘要保留独立文件／批次子目录。缺资源只暂停依赖它的模块或照片，不重建近似水印、不把预览冒充原片、不阻塞无关已确认照片。

## 7．封装和回归

`scripts/build_skill.py` 从明确白名单生成独立目录、ZIP 和源文件摘要清单。默认不安装到全局 Skill 目录；安装与宿主发现、实际加载是另外的状态。真实活动资料、运行数据库、工作缓存、备份和账号均排除。分发副本由单一源生成，不手工维护第二套规则。

移动到独立目录后，用合成素材运行 `photo_inventory.py` 与 `test_contract.py`。后者保留所有夹具，检查错图蒙版、方向映射、摘要漂移、旧确认、未测 QA、缺少基础候选与输出、保护核心被改等失败情形。它不证明照片修得好。更改契约后先运行这些可观测行为检查，再按受影响方法做真实代表样片。
